# Changelog - Tape Deck Server

## 2026-10-15: Project created, v1.0.0 ready to release

- **What it is** (Andy: "this little Python server that serves as a tiny headless Docker container or app where I can let people serve their own files … so I can stick it on GitHub and release it"). His choices: a server for the app alone, not the web player; its own public repository; Docker and a plain script; MIT.
- **`tape_deck_server.py`**: scans Artist/Album/tracks as the Tape Deck generator does (discs nest, folders give the artist and album, tags the title and length, a tag cache by path, size and date), makes 160-pixel covers from a folder image or the tracks' art, and serves the catalogue (gzipped, with an ETag), the audio with ranges and If-Range, the covers, `/favs`, `/login`, `/logout` and `/health`. The folder is read again every 15 minutes.
- **Two passwords, not one.** The first design had one password and treated anyone signing in with it as a guest, as Tape Deck's own server does; behind a reverse proxy, where nobody can be placed by address, that left the owner without favourites. So `TAPE_PASSWORD` is the owner's and `TAPE_GUEST_PASSWORD` a guest's, the cookie signed for one or the other.
- **Docker asks everyone.** In the image a caller through a published port arrived from the bridge's private address, which counted as home and skipped the password; the image now sets `TAPE_HOME_NETWORKS=none`, and the CI checks a published port is asked.
- **Checked:** `tests/test_server.py`, 17 tests, with Python 3.15 with and without mutagen and Pillow (the cover test skipped without). The image built and run under colima: 233 MB, the user `tapedeck` (Debian already has a `tape` group), the password asked through the published port. The Tape Deck app in the iOS simulator against the script (signed in as a guest, the catalogue read, an album it hadn't had downloaded and played) and against the container (signed in as the owner, 6 tracks and the cover).
